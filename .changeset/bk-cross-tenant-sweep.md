Cross-tenant sweeps: a first-class, safe way for a reconciler to find stuck work in every tenant under RLS (BK-022).

A reconciler has to answer a question no tenant-scoped query can answer — *which rows, anywhere, are still `PROCESSING`?* With Postgres RLS the application role only ever sees one tenant, and `tenancyExtension` refuses unscoped queries, so application teams were writing the `SECURITY DEFINER` escape hatch by hand. It is now supplied, hardened, and bounded.

- **`crossTenantScanSql({ name, table, tenantColumn?, columns, where?, role, owner?, maxRows? })`** generates the migration, in the style of `rlsPolicySql`: a `SECURITY DEFINER` function that returns **identifier columns only** (`tenant_id` + `id`, plus up to two more you declare) across every tenant. It pins `SET search_path = pg_catalog, <schema>` inside the function (a `SECURITY DEFINER` function without one is a privilege-escalation hole), is `STABLE` / `PARALLEL SAFE`, validates and quotes every identifier (nothing is interpolated raw; a `where` containing a semicolon, a comment or a `$` is refused), drops and recreates idempotently, and ends with `REVOKE ALL ON FUNCTION … FROM PUBLIC` + `GRANT EXECUTE` to the role(s) you name. The generated SQL says in a comment what it is: a deliberate RLS bypass, safe only because it returns identifiers and never tenant data. Its `owner` must be a role the policies don't reach (`BYPASSRLS`/superuser) — `rlsPolicySql` sets `FORCE ROW LEVEL SECURITY`, so a function owned by the table owner would return nothing.
- **`crossTenantScan(client, name, args?)`** calls it and returns typed `{ tenantId, id }[]`. It is a raw query and a deliberate bypass, so — unlike the internal `set_config` statement — it gets **no** exemption from the `PRISMA_RAW_IN_TENANT` guard: it refuses to run at all while a tenant is in scope (`PRISMA_CROSS_TENANT_IN_TENANT`), because a sweep is central code by definition.
- **`crossTenantSweep({ client, scanFunction, handle, run?, limit?, maxItems?, onError? })`** pages through the scan and runs `handle` for every row **inside its own tenant's context** (grouping consecutive rows of a tenant into one `run`), so the scoped client and the RLS policies apply again and the item can be read and updated normally. `run` defaults to putting the tenant in the context; pass `(id, fn) => tenancy.run(id, fn)` for the real tenant record and the `tenancy:switched` hook. Failures are isolated per item.
- **Guard rails.** The runtime refuses a deployed function whose returned columns are not a subset of the ones the caller declared (`PRISMA_CROSS_TENANT_SCAN_SHAPE`) — a function widened after the fact to also select tenant data never reaches application code — and refuses a NULL identifier. The scan is bounded three times over: `maxRows` is clamped inside the function, `(p_after_tenant, p_after_id)` is an ordered cursor, and the sweep adds `limit` (per page) and `maxItems` (per sweep, default 10 000, reported as `truncated`). `columns` is capped at four.
- **Without RLS none of it is needed**: pass your own central query as `scan` and keep the paging, the grouping and the per-tenant execution. Documented as the simpler default.

Verified against real PostgreSQL: in-process (pglite) in the package's own suite, and end to end in `apps/pg-integration` against a server with a non-superuser `basalt_rls_app` role — with RLS on the app role sees nothing unscoped, the function returns identifiers for every tenant, the grouped sweep processes each row under the right tenant scope and updates it, a non-granted role cannot execute the function, and the function cannot be used to read tenant data.
